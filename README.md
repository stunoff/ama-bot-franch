# АМА Франчайзинг · Python 3.12 + MySQL 8.4 + Docker

Рабочая серверная реализация ядра и основных сценариев ТЗ редакции 1.0 от 16.11.2026. Это версия 0.11.1 для технического пилота, **не полное выполнение всех 68 критериев приёмки**. Реализованные функции и оставшиеся части подробно перечислены в [docs/COVERAGE.md](docs/COVERAGE.md). Исходное ТЗ включено в `docs/SPECIFICATION.txt`.

Версия 0.3.0 добавляет второй этап: [автоконсультацию, лендинги и продажи](docs/SALES-0.3.0.md). [Обновление с 0.2.0](docs/UPGRADE-0.3.0.md). Требуются опубликованные реальные материалы и настройки очередей; цены и обещания не придумываются сценарием.

## Что работает

- Единое состояние Telegram/MAX в MySQL; подтверждённые люди отдельно от аккаунтов, ФП, бренды, физические предприятия и связи брендов.
- Один активный клиентский маршрут на «ФП + бренд», несколько предприятий внутри него; серверные роли с областями, сроком назначения и проверкой чата/темы.
- Рабочие карточки и самостоятельные пункты: исполнитель, принимающий, версия, история, сроки, ожидание, возврат, отмена. Загрузка, сдача и приёмка разделены.
- Передача ответственности с подтверждением получателя. До подтверждения исходный владелец сохраняется.
- Файлы, фото и Telegram-альбомы: сохранение на диске с SHA-256, немедленная очередь доставки ответственному, защита от повтора, отдельная видимость внутренних материалов.
- Мастер клиентского запроса с кнопками: предприятие/бренд → маркетинг/другой вопрос → тема → уточнения → предпросмотр → создание. Состояние формы хранится в БД. Первичная очередь — маркетинг либо сопровождение, профильный маршрут хранится как рекомендация.
- Персональное ознакомление: 143 карточки из ТЗ, модули 0–11, назад/дальше/позже, сохранение версии и подтверждения, без экзаменов. Материалы должны быть утверждены владельцем до публикации.
- Лиды после согласия, квалификация, отдельные этап/ожидание/исход; явный отказ сохраняется при повторном входе. Бренд до квалификации можно не выбирать.
- Договорная готовность, редакции комплекта, подписи текущей редакции и проверенные платежи в копейках. Успех сделки и принятие куратором — независимые факты.
- Одна цепочка автоматических касаний лида, максимум два доставленных сообщения; отправка по утверждённому календарю продаж и шаблонам. Ответ отменяет ожидающие касания; ручная дата, договор и отказ подавляют автоматику.
- Подтверждённый куратором состав проекта: только выбранные применимые работы; действующему объекту не создаётся вымышленное открытие.
- Платное предложение с версией, сроком, правилом старта и подтверждением назначенного ФП. Предложения разрешены только в установленных профильных чатах. Долг ведётся отдельно, с историей оплат и отсрочек.
- Цифровой паспорт: независимый выбор мессенджеров телефона/управления, отдельные подтверждения компонентов и контрольного теста; Служба заботы обязательна без КЦ. Допуск к открытию проверяет персональное ознакомление и обязательные зависимости.
- Рассылка после предпросмотра аудитории: одна публикация на брендовый чат, согласованное окно отправки партнёра. Когортная аналитика продаж не смешивает старые успехи с новыми лидами.
- `/af_settings` из управляющего чата, защита последнего администратора, версии справочников, проверка маршрута тестовой доставкой, перенос чата с сохранением работ.
- Транзакционные inbox/outbox, дедупликация входящих обновлений, журнал, устойчивые таймеры и диагностика ошибок.

## Быстрый запуск

Нужны Docker с Compose v2, токен Telegram и/или MAX, публичный HTTPS-адрес с доступом к этому серверу. Само создание ботов в мессенджерах не входит в код.

```bash
cp .env.example .env
# Заполните .env: MYSQL_PASSWORD, MYSQL_ROOT_PASSWORD, токены, webhook secrets и PUBLIC_URL.
# Для случайного пароля/секрета: python3 -c 'import secrets; print(secrets.token_hex(24))'
docker compose up -d --build
docker compose exec api python -m ama.cli seed
curl http://127.0.0.1:8000/health
```

Compose поднимает `mysql`, одноразовую миграцию, `api` и `worker`. API опубликован только на loopback; внешний порт MySQL задаётся `MYSQL_PORT` (по умолчанию 3306). База и файлы находятся в именованных volumes. `.env` и реальные клиентские данные в архив не включены.

Пароли MySQL в `.env` используйте в hex-формате: они включаются в URL подключения. `docker compose down` сохраняет данные; `down -v` удаляет их.

Подключите HTTPS reverse proxy (пример для Caddy — `scripts/Caddyfile.example`). Затем:

```bash
docker compose exec api python -m ama.cli register-webhooks
```

Webhook секреты должны быть независимыми случайными строками длиной минимум 16 символов. Конечные адреса: `/webhooks/telegram`, `/webhooks/max`. Неправильный секрет возвращает 403; повтор события подтверждается без второго исполнения.

## Первый администратор и настройка

Добавьте бота в реальный управляющий чат и выдайте право отправки. Для Telegram используйте числовые ID пользователя/чата; для MAX — ID из его API. Выполните на сервере, подставив реальные значения:

```bash
docker compose exec api python -m ama.cli init-admin \
  --platform telegram --user-id YOUR_USER_ID --chat-id YOUR_MANAGEMENT_CHAT_ID
```

Команда отправляет тестовое сообщение и активирует управляющий маршрут только после успешного ответа API. Для Telegram-темы дополнительно используйте `--topic TOPIC_ID`. После первого назначения повторная инициализация блокируется. В управляющем чате откройте `/af_settings`.

В версии 0.2.0 настройки и инструменты сотрудников открываются кнопками: пошаговые формы, сохранённые черновики, предпросмотр и подтверждение, рабочие панели, CSV-выгрузки. [Инструкция по интерфейсу](docs/CHAT_UI.md). JSON-команды остаются для совместимости: [docs/COMMANDS.md](docs/COMMANDS.md).

Обновление работающей установки: [docs/UPGRADE-0.3.0.md](docs/UPGRADE-0.3.0.md). Повторное создание администратора и очистка volumes не требуются.

Перед подключением клиентов заполните реальные роли и чаты, область брендов/предприятий, опубликованные календари и маршруты, согласие, материалы и коммерческие условия. `seed` создаёт шесть брендов с **выключенными продажами**, а курс — как **неопубликованный черновик**. Чужие коммерческие суммы, ссылки и даты не подставляются.

## Проверки

```bash
python3.12 -m venv .venv
. .venv/bin/activate
pip install -c requirements.lock -e '.[test]'
DATABASE_URL=sqlite:// pytest -q
ruff check ama tests
```

SQLite используется только в быстрых тестах; основной сервис работает с MySQL. Интеграционные тесты направляйте только на отдельную базу `ama_test`: тестовый набор очищает её таблицы.

```bash
TEST_DATABASE_URL='mysql+pymysql://USER:PASSWORD@127.0.0.1:3306/ama_test?charset=utf8mb4' \
DATABASE_URL=sqlite:// pytest -q
```

Фактический протокол проверки поставки — [docs/TEST_REPORT.md](docs/TEST_REPORT.md). Транспортные тесты подменяют API Telegram/MAX; они не означают испытание живых чатов.

## Эксплуатация

```bash
docker compose logs -f --tail=100 api worker
docker compose exec api python -m ama.cli diagnostics
scripts/backup.sh /absolute/path/to/backup
```

Детали восстановления, файлов, очереди и неопределённых отправок: [docs/OPERATIONS.md](docs/OPERATIONS.md).

Сетевая отправка не может гарантировать exactly-once при тайм-ауте внешнего API. Состояния `sending` после сбоя и `uncertain` требуют сверки с чатом; они не повторяются вслепую. Это предотвращает автоматические дубли ценой ручной обработки неопределённого результата.

Если в сети сборки установлен собственный корневой сертификат, Dockerfile принимает секрет `build_ca` без отключения TLS:

```bash
docker build --secret id=build_ca,src=/path/to/trusted-ca-bundle.pem -t ama-franchising:local .
docker compose up -d --no-build
```
