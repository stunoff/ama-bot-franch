# Эксплуатация

## Архитектура

`api` аутентифицирует webhook и фиксирует inbox до ответа 200. `worker` разбирает события, исполняет доменные операции в транзакции, сохраняет материалы, проверяет таймеры и отправляет outbox. Повторные update/callback/file защищены устойчивыми ключами. Изменения карточки и история атомарны; ошибка составной команды откатывается через SAVEPOINT.

MySQL 8.4 — основной источник состояния. Используются FOR UPDATE, SKIP LOCKED и DATETIME(6). Физические площадки отделены от брендов. Файлы находятся в volume files; в БД — автор, пункт, источник, видимость, SHA-256 и фактический статус сохранения.

## Диагностика и повторы

```bash
docker compose exec api python -m ama.cli diagnostics
docker compose exec api python -m ama.cli retry inbox EVENT_KEY
docker compose exec api python -m ama.cli retry attachments ATTACHMENT_ID
docker compose exec api python -m ama.cli retry timers TIMER_ID
docker compose exec api python -m ama.cli retry outbox OUTBOX_ID
```

Перед повтором устраните причину: права, маршрут, календарь, размер/тип файла либо доступность мессенджера. Для таймера без управляющего маршрута статус blocked — сигнал не удаляется, после настройки его нужно повторить.

Состояния отправки: pending → sending → sent. Временное отсутствие соединения и 429 повторяются с задержкой и лимитом. Неопределённый исход — uncertain. После завершения процесса запись sending также считается неопределённой: она не подбирается автоматически другим worker.

У Telegram/MAX нет общего гарантированного ключа идемпотентности отправки. Проверьте фактический чат и затем:

```bash
# Сообщение уже есть:
docker compose exec api python -m ama.cli mark-delivered OUTBOX_ID REAL_MESSAGE_ID
# Проверили, что его нет:
docker compose exec api python -m ama.cli retry outbox OUTBOX_ID --confirmed-not-delivered
```

Эти операции журналируются. Нельзя объявлять exactly-once внешнюю отправку при сетевом тайм-ауте. Для отправок с подтверждённым отсутствием повтор выполняется в тот же разрешённый маршрут; новое состояние повторно проверяется перед сетью.

## Резервная копия и восстановление

Запускайте `scripts/backup.sh /absolute/path/to/backup-directory` из корня проекта. Скрипт останавливает запись api/worker, сохраняет MySQL и files, затем запускает процессы. Нужное окно обслуживания, шифрование резервов, размещение инфраструктуры и сроки хранения утверждает владелец. `.env` и доверенные сертификаты сохраняйте отдельно в защищённом хранилище.

Восстановление выполняется на отдельном тестовом стенде перед использованием в рабочем:

1. Проверить SHA-256 архивов, остановить api/worker, запустить только mysql.
2. Восстановить SQL: `gzip -dc BACKUP/mysql.sql.gz | docker compose exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" exec mysql -uroot ama'`.
3. Распаковать files.tar.gz в volume files с владельцем UID/GID 10001. Например, подключить каталог резервов read-only и volume files в одноразовый контейнер; восстановление запускать только в выбранный проверенный volume.
4. Выполнить миграции, проверить diagnostics и неизвестные исходы sending/uncertain.
5. Запустить api/worker, проверить health, права и одну тестовую доставку. Повторяются только недоставленные актуальные события.

Испытание аварийного восстановления на инфраструктуре заказчика ещё требуется; наличие скрипта его не заменяет.

## Файлы и протоколы

Лимит по умолчанию — 20 MiB. Разрешены jpg/jpeg/png/webp/pdf/doc/docx/xls/xlsx/zip/txt/mp4; это технический лимит поставки, владелец должен согласовать политику. Файлы сохраняются под внутренним ID, не под пользовательским путём. Автоматическое исполнение документов отсутствует. Антивирусный шлюз в поставку не включён.

Скачивание допускает только HTTPS-домены адаптеров, не следует произвольным redirect. Если реальное CDN мессенджера отличается от allowlist, адаптер вернёт ошибку; расширяйте список после проверки документации/адреса, не разрешайте любые URL.

Файлы внутреннего контура не выдаются через `/files` в клиентский чат. Для внешней пересылки внутреннего материала отдельный workflow согласованной публикации ещё нужно добавить. Не размещайте секреты доступа в сообщениях/материалах; ввод токенов — `.env` на сервере.

## Обновления

Снимите резервную копию, соберите образ, выполните `docker compose up -d`. Миграции запускаются до api/worker; начальная схема зафиксирована отдельным revision. Будущие изменения добавляйте новой миграцией, не редактируя 0001 действующей БД.

Справочник календаря не переписывает уже сохранённые сроки. Смена чата — через replace_binding после probe, а не правкой внешнего ID в БД. Смена человека и смена его аккаунта — разные операции: прогресс привязан к person_id. Привязку нового аккаунта тому же человеку выполняет уполномоченный администратор только после проверки личности.
