# Патч 0.11.0 → 0.11.1

Патч исправляет 9 групп замечаний аудита первичной настройки. Изменений схемы MySQL нет: Alembic остаётся на 0011. Зависимости Python, Compose, Dockerfile, порты, `.env` и файловое хранилище патч не изменяет.

## Применение на сервере

Сохраните резервную копию БД, файлов и текущих исходников. Скопируйте архив патча на сервер и распакуйте, например, в `/tmp/ama-patch-0.11.1`. Архив — набор изменённых файлов и установщик, не полный проект.

Из каталога действующего проекта `/opt/franch-bot`:

```bash
python3 /tmp/ama-patch-0.11.1/ama-upgrade-0.11.1.py --check
docker compose stop api worker
python3 /tmp/ama-patch-0.11.1/ama-upgrade-0.11.1.py --apply
docker compose build api worker
docker compose up -d --force-recreate api worker
docker compose ps
docker compose exec api python -m ama.cli diagnostics
```

Установщик рассчитан именно на 0.11.0, сравнивает SHA-256 всех изменяемых файлов и при конфликте останавливается до записи. Локально изменённые исходники нужно согласовать вручную. Исходники до применения сохраняются в `backups/source-*`, добавленные файлы перечислены в manifest.json этой копии. Повторное применение безопасно. `.env`, Compose и Dockerfile сохраняются, включая локальные порты.

Альтернатива — стандартный unified diff:

```bash
patch --dry-run -p1 < /путь/ama-0.11.0-to-0.11.1.patch
# После успешной проверки, при остановленных api и worker:
patch -p1 < /путь/ama-0.11.0-to-0.11.1.patch
```

Используйте один способ применения. Установщик дополнительно проверяет контрольные суммы и сохраняет копию исходников. Копирование содержимого каталога changed-files поверх локально изменённого проекта без сверки не рекомендуется.

## Восстановление администратора

При отсутствии доступного администратора `init-admin` использует существующего человека по аккаунту и совместимую управляющую привязку. История аккаунта не переносится. Просроченные назначения и назначения другого bot_id больше не блокируют bootstrap. Отключённые аккаунты автоматически не восстанавливаются.

Если действующий администратор уже есть, повтор по-прежнему блокируется. Для явного восстановления управляющего маршрута **того же администратора** используйте:

```bash
docker compose exec api python -m ama.cli init-admin \
  --platform telegram \
  --user-id 7321973346 \
  --chat-id 7321973346 \
  --recover
```

Это пример личного диалога. Для группы подставьте её фактический отрицательный ID; для темы добавьте `--topic ID_ТЕМЫ`. Положительный ID не превращается в групповой автоматически. Если привязка этого адреса имеет другое назначение/область, команда остановится. При неудачной отправке настройки откатываются. При неопределённой доставке сначала сверьте сообщение, затем повторяйте.

`--recover` не назначает другого человека вместо существующего доступного администратора. При нескольких администраторах восстанавливается только маршрут аккаунта, у которого уже есть пригодное системное назначение.

## Подключение группы

1. Добавьте бота и проверьте права на отправку; для управления форумными темами нужны соответствующие права Telegram.
2. Создайте привязку с реальным ID группы/темы и назначением. `management` — управление/настройки, `support` — рабочее место куратора. Назначения сотрудников задаются отдельно.
3. Отправьте тест доставки. Очередь не означает успех: дождитесь сообщения именно в нужной группе/теме.
4. Нажмите «Обновить статус чата». После успешного теста отдельно нажмите «Подключить чат…».
5. Опубликуйте календарь и рабочий маршрут с подходящими ролями и активными аккаунтами. Проверьте новое обращение из клиентского чата.

Устаревшие тесты после изменения ID/версии отменяются до отправки. Подтверждение фактически доставленного probe через CLI/UI одинаково выставляет verified только для соответствующей текущей версии и адреса. Клиентская активация требует действующего ФП текущего бота/области с активным аккаунтом соответствующего мессенджера.

При замене группы опубликованные маршруты теперь обновляются и версионируются вместе с переносом существующих работ. Старые неопределённые отправки не повторяются автоматически.

## Уже существующие ошибки настройки

Патч не угадывает адресатов и не переписывает старые неверные настройки автоматически. Если замена группы уже выполнялась до патча, проверьте опубликованные маршруты и явно выберите новую проверенную привязку в настройках. Неверный положительный ID группы исправляется владельцем на фактический ID. Старые failed/blocked записи не отправляйте массово без проверки получателей и фактической доставки.

Проверка готовности:

```bash
docker compose exec api python -m ama.ops_cli preflight
```

Успешный healthcheck не заменяет проверку worker, webhook, групп и ролей. Версия 0.11.1 требует новых свидетельств живой приёмки; прежние свидетельства автоматически не засчитываются.

## Диагностика и секреты

Регистрация webhook теперь требует хотя бы один токен и сообщает безопасные HTTP-код/описание отказа Telegram/MAX. Публичный URL допускает префикс, но не логин, query или fragment. Для Telegram секрет — 16–256 символов A–Z, a–z, 0–9, `_`, `-`.

HTTP-логи и операторские ошибки маскируют токены. Старые логи патч не изменяет, уже раскрытый токен не отзывает. Ранее опубликованный токен перевыпустите в BotFather, замените в `.env`, пересоздайте api/worker и заново зарегистрируйте webhook.
